# Versioning Policy

Renoir uses [Semantic Versioning](https://semver.org/) (MAJOR.MINOR.PATCH).

## What counts as a breaking change

Renoir's primary consumers are C/C++ and Python callers through FFI, not
just Rust API users. Both layers matter, and the C ABI is treated as a
public, stable surface.

The following are **breaking** (require a MAJOR bump):

- Removing or renaming a C function exported from `librenoir.so`
  (anything `#[no_mangle] pub extern "C"`)
- Changing the layout (field order, type, or size) of a `#[repr(C)]`
  struct in `src/ffi/types.rs` that crosses the FFI boundary
- Changing the meaning or range of `RenoirErrorCode` values (the C enum is
  generated by cbindgen; a reorder, insertion, or removal of a variant
  changes numeric values that C/C++/Python code may compare against)
- Renaming or repurposing an existing FFI function's parameters in a way
  that changes call compatibility
- Changing the on-disk/shared-memory wire format for message headers or
  ring control blocks in a way that breaks interoperability between a
  new process and an old process (e.g. `MessageHeader` layout changes)
- Removing a public Rust API item that external Rust consumers can reach
  (we keep the Rust API under the same policy as the C ABI, since the
  crate is published)

The following are **minor** (require a MINOR bump):

- Adding a new FFI function, `#[repr(C)]` struct, or Rust `pub` item
- Adding a new enum variant to `RenoirErrorCode` at the end of the enum
- Adding a new field to a `#[repr(C)]` struct **at the end** only if the
  generated C header consumers can tolerate the size change safely; in
  practice for Stage 1 this is still treated as breaking unless the field
  is purely additive and zero-initialized — decide per change, and
  document the decision in the changelog

The following are **patch** (PATCH bump):

- Bug fixes that do not change any public API or wire format
- Performance improvements
- Internal refactors with no API change

## Before 1.0

Before the 1.0.0 release, MINOR bumps may include breaking changes to the
Rust API only if the C ABI remains stable; breaking C ABI changes still
require a MAJOR bump even pre-1.0, because our consumers link the shared
library directly.

## Process

- Every change that touches the C ABI or wire format updates
  `CHANGELOG.md` and notes the compatibility impact.
- `cargo publish` is only run after `cargo publish --dry-run` is clean and
  the changelog/version bump is reviewed.
